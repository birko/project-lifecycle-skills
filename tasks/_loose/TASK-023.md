# `/tasks init` cannot reconcile a config written by an older version of itself

## Context

Spawned from TASK-021, which gave `adopt-project` the rule *delegate to the owner's init whether or
not the artifact is present, because the inits are delta-based*. Checking that assumption against
[[tasks]]'s [verbs/init.md](../../skills/tasks/verbs/init.md) shows it does not currently hold:

- The verb's own summary: *"Idempotent: if both files already exist, report that and change nothing
  (suggest `/tasks triage` to refresh the dashboard instead)."*
- Step 3: *"Don't overwrite an existing config"*, with a conflict path only for a **mode** mismatch.
- Its edge cases cover a tree with task files and **no** `.config.yml` — a pre-skill tree — but not a
  `.config.yml` that exists in an **older shape**.

So the delta `init` can express is "the file is missing" or "the mode disagrees". A config written
before a field existed reports as nothing-to-do. Concretely, `Presenter/tasks/.config.yml` was
generated by `/tasks import` on 2026-05-28 and has no `integration:` field at all; a full
`adopt-project` pass over that repo — even one obeying TASK-021's new rule — would delegate here and
be told there is nothing to reconcile. The field then gets guessed from `git log`, which is the
failure TASK-021 exists to stop.

This is the general shape, not one field: `integration:` is simply the first field the config gained
after repos started using it. Every future field lands in the same hole, and the skill that owns the
shape is the only thing that can know a shape is old.

**Do not fix this by having `adopt-project` write the field.** That is the hand-rolling the layer's
Owner column exists to prevent, and it would put the config's shape in two skills.

## Acceptance criteria

- [ ] `/tasks init` on an existing `.config.yml` reconciles it against the current template: fields the template has and the file lacks are **added**, with their documented default and comment
- [ ] Values already present are never changed — reconciliation adds, it does not re-decide. A field whose value is a real choice (`integration:`) is **asked** rather than defaulted silently when it is absent
- [ ] The verb reports what it reconciled, so a caller (and `adopt-project`'s report) can distinguish "nothing to do" from "brought up to date"
- [ ] "Both files exist → change nothing" is corrected: it is true only once the config matches the current shape. The idempotence promise stays intact — a second run on a reconciled config writes nothing
- [ ] A comment-only or user-annotated config survives reconciliation with its comments intact; this is a file people hand-edit
- [ ] `templates/config.yml` is the single source of the field list — the verb reads the template rather than carrying its own copy of what a config contains
- [ ] `skills-lint` and `skills-lint-test` stay green

## Out of scope

- Mode *changes* — `/tasks migrate` owns that, and this task must not become a second path to it.
- Reconciling the task **files** (EPIC/STORY/TASK frontmatter) against their templates; same class of problem, bigger blast radius, and it needs its own decision about what an old task file even means.
- `adopt-project`'s side of the rule → TASK-021.
